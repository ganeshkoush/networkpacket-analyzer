# PacketMind — Project Guide

AI-powered network traffic analysis/investigation desktop app. Built incrementally in phases; only implement what the current phase asks for.

## Layout
- `desktop/` Tauri 2 + React + TS + Tailwind 4 (Vitest). UI only — no analysis logic.
- `backend/` FastAPI + SQLite. `app/capture` (live capture), `app/analysis` (parsing/aggregation), `app/detection` (explainable detectors), `app/ai` (Gemini investigator), `app/models` (ORM/schemas), `app/services` (orchestration), `app/utils`.
- `tests/` cross-component tests; `backend/tests/` backend unit tests.

## Commands
- Backend: `cd backend && .venv/bin/python main.py` (127.0.0.1:8765); tests: `.venv/bin/pytest`
- Desktop: `cd desktop && npm run tauri dev`; tests: `npm test`; build check: `npm run build`

## Architecture principles
1. Packet processing stays local. Never send a whole PCAP to the LLM.
2. Parse and aggregate locally first; send only structured evidence to the LLM.
3. The LLM (Gemini, behind `app/ai/provider.py`) is the reasoning/investigation layer, never the raw packet parser.
4. Detection algorithms must be explainable; every finding carries evidence and a confidence score.
5. AI findings must reference evidence. Never state traffic is definitely malicious — use hedged, confidence-scored language.
6. Keep UI, networking, detection, and AI logic in separate modules.

## Safety rules
- No destructive network actions. No automatic IP blocking.
- Never execute commands suggested by the AI. AI tools are a fixed, read-only allowlist of analysis functions.
- Security-sensitive operations (live capture, file access) must be explicit and user-initiated.
- Backend binds to loopback only. Captures/reports/DB are git-ignored.
- Secrets (e.g. `GEMINI_API_KEY`; model via `GEMINI_MODEL`) come from environment/`.env`, never committed.

## Conventions
- Python: type hints, pydantic models at boundaries, pytest for every module.
- Frontend: function components, Tailwind utilities, backend access only through `src/api.ts`.

## Analysis engine (backend/app/analysis)
- `analyze_pcap(path)` (service.py) streams the capture once via `PcapParser` -> `PacketRecord`; each analyzer (`*_analyzer.py`, `statistics.py`) has `add(record)` / `result()` and keeps only aggregates with caps.
- Result models live in `app/models/analysis.py`. Output is aggregated evidence only - never raw packets.
- `domain_analyzer.py` maps per-client DNS A/AAAA answers (`DnsInfo.answers`) to later TCP/UDP flows -> `AnalysisResult.domain_statistics`. It is inference, not observation: UI/docs say "domain/hostname/service", never "URL visited".
- Retransmission/duplicate-ACK/SYN-ratio values are heuristic indicators, not verdicts.
- Connection tracking: `connection_analyzer.py` groups packets into bidirectional flows; `connection_tracker.py` holds pure helpers (`flow_key`, stable `connection_id`, `tcp_state`, `filter_connections`). TCP state is derived from captured packets only (a mid-connection capture is `UNKNOWN`, not `ESTABLISHED`). `result()` enriches connections via lookups into `TcpAnalyzer.flow_retransmissions` and `DomainAnalyzer.domain_for_flow` - never duplicate that logic. `domain` is optional (no DNS -> `None`, connection stays valid). Served by `GET /api/analyses/{id}/connections[/{conn_id}]`; connections live in the in-memory `AnalysisResult` (no separate table).
- Handshake timing: `ConnectionAnalyzer` stores the first few SYN/SYN-ACK/early-ACK packets per connection as tuples; `connection_tracker.resolve_handshake` pairs them by seq/ack numbers at `result()` time (order-independent). Latencies exist only for matched packets; otherwise `handshake_status="incomplete"` + a reason and no estimate. Retransmitted SYN/SYN-ACK use the earliest copy, so times include that delay (flagged by the retransmission counts). Per-domain averages (`ConnectionSummary.handshake_by_domain`) cover all tracked connections, not just the reported top N.
- Latency (`latency_analyzer.py`, `performance.py`, `AnalysisResult.performance_statistics`): handshake time, TCP RTT, TLS hello time and cleartext-HTTP response time are separate fields - never present handshake time as response time. RTT = data segment -> exact pure-ACK (piggybacked ACKs excluded; retransmitted/reordered segments and anything cumulatively acked through them are dropped; no sample if ACK is stamped earlier). HTTP/TLS are recognised from content only via `PacketRecord.app_hint` (`classify_tcp_payload`: kind only, no content kept); HTTPS gets no response time. DNS lookup latency is recorded in `DnsAnalyzer` (retransmitted queries untimed). Values are `None` (never estimated) when packets are missing; `measurement_confidence` = RTT sample count (HIGH>=10, MEDIUM 3-9, LOW 1-2, UNAVAILABLE 0; one step lower if >10% segments ambiguous). Tests: `make_pcap(..., sort=False)` keeps file order (default sorts by time!).
- Web Activity dashboard (`/web` page, `app/analysis/web_activity.py`, `app/models/web_activity.py`, `GET /api/analyses/{id}/web-activity[/{domain}]`): joins `DomainActivity` + `DomainPerformance` + connections at request time; **search/sort/health filter/paging happen in the backend, React only renders** (no analysis logic in the UI). Health (`assess_health`, thresholds in `HealthThresholds`) is a heuristic with listed reasons; `unknown` when nothing is measurable. Per-domain time series (`PerformanceStatistics.series`, `exclude=True` so it never bloats the result bundle) come from all tracked flows; traffic bins are exact per-packet counts from `DomainAnalyzer` with adaptive bin width. Charts use `components/charts/SeriesChart.tsx` (hand-rolled SVG, no chart library).
- Historical baselines (`analysis/baseline.py` pure stats, `services/performance_history.py` SQLite store, migration v2 `perf_sources`/`perf_observations`, `models/baseline.py`): one observation per (capture, domain), keyed by capture SHA-256 so re-analysis replaces instead of double-counting; only domain names + aggregate numbers are stored (no packets/IPs), recording is wrapped so it can never fail an analysis, `PACKETMIND_PERF_HISTORY_ENABLED=false` turns it off, clearing needs `confirm=true`. Recording goes through `AnalysisJobManager(history=...)` / `LiveCaptureManager(on_session_end=...)`, so tests (which get an isolated per-test history via the autouse `history` fixture) never touch the real DB. Anomalies are *derived* at read time: current capture vs the previous 30 observations of the same domain+metric. Latency: log-scale robust z (median/MAD, floor `min_log_sd`); rates: binomial z widened to observed spread; plus percentile gate (p95 of *inlier* history - earlier anomalies are not learned from), min baseline observations (5), min samples in the current capture, relative+absolute effect floors, upward changes only. Never flag with an immature baseline; `insufficient_*` statuses say why. Confidence/severity reuse `detection/severity.py`; severity is capped by confidence.
- Correlation (`backend/app/correlation/`, `GET /api/analyses/{id}/correlations?finding_id=`, "Related Events" on the finding page): links security findings to performance changes that are **"Potentially related" - never "caused by"** (no causal wording anywhere; every record carries evidence + the non-causation caveat; confidence capped at 0.85). Data: bounded in-memory `PerformanceStatistics.flow_samples`/`lookup_samples` (per-connection/per-lookup timing; `exclude=True`, never serialised; uniformly thinned with `flow_sample_stride` for huge captures). Per rule, evidence is tried in order: (1) the finding's time window vs the *rest of the same capture* within its scope (works on a first capture; the flagged source is excluded where circular; SYN-flood windows are narrowed to the actual burst with `find_burst` because the detector's first/last-seen spans background SYNs too), (2) same-connections co-occurrence for network-wide findings without a window (retransmissions, resets), (3) capture-level match with history anomalies (lower confidence). Tests are `measures.py` (robust log z for latency using a *run* of consecutive affected samples so a short slowdown is not diluted; Poisson z for rates; two-proportion z for failure share), each with minimum-data gates and effect-size floors; `not_evaluated` / `no_related_change` explain what was checked. Add a new correlation by adding a rule to `RULES` in `engine.py`.
- Process mapping (`backend/app/platform/{base,macos}.py`, `services/process_mapper.py`, `api/processes.py`, `docs/process-mapping.md`): a packet capture never identifies the application - only OS snapshots do (macOS: read-only `lsof` + `ps`, absolute paths, no shell, no elevation; own user's processes only). Never fabricate names: unmatched -> "Process information unavailable" with the reason. Snapshots are **explicit user actions only** (`confirm=true`), memory-only (never SQLite/disk), and a connection is matched only to snapshots taken while it was active (± slack), by full endpoint pair; weaker matches are LOW. Application name = outermost `.app` bundle in the executable path, else the plain process name. New OS = new module + register in `get_process_source()`. Tests use a mocked runner/source; the autouse `process_mapper` fixture guarantees tests never run real OS tools. Process data lives only in `/web-activity/{domain}/applications`, never in the analysis result.
- Network Map (`/map`, `GET /api/analyses/{id}/network-map`, `backend/app/analysis/network_map.py`, `desktop/src/components/map/`, `pages/NetworkMap.tsx`): local host -> (applications) -> domains -> IPs -> ports. **The backend builds, filters (search, protocol, health, time range, local host) and budgets the graph; React only draws it** and handles clicks. It shows the connections the analysis keeps detail for (largest by traffic), never thousands of nodes: lower-traffic destinations fold into one "more destinations" node (node budget), except ones a finding names. The "local" end of a connection is its private endpoint. State is explainable: *suspicious* = a finding names the remote address, *degraded* = failed handshake / >=3 retransmissions / a domain the web-activity health rules rate fair-poor, *healthy* = measured and fine, *unknown* = nothing measurable (never shown as healthy). Edge/node latency is RTT, else handshake, never mixed (`latency_kind`). Application nodes only when `include_applications` and OS snapshots matched. Graph library: `@xyflow/react` (React Flow), lazy-loaded with the page; layout is our own deterministic layered function (`lib/mapLayout.ts`) and nodes declare `width/height/handles` so edges render without DOM measurement. **Layout/readability rules (found by looking at it in a real browser):** an address with a single port is one node labelled `ip:port` (port nodes only when an address has several; >8 ports fold into `+N more ports`); addresses with no DNS name hang under one `No DNS name` group in the domain row so every edge goes down exactly one row (rows = longest-path rank, `lib/mapLayout.ts`); rows wider than 7 wrap into stacked sub-rows; edge labels are anchored just above the node the line points to (not at the curve midpoint) and staggered by >= label width when several lines reach one node, which keeps labels from colliding; labels hide below 0.45 zoom with an on-canvas hint. **React Flow gives nodes `pointer-events:none` unless a click handler is registered** (we turned off drag/select), so real mouse clicks fell through to the pane while jsdom tests passed: keep `onNodeClick` and the pointer-events test. Check map changes in the actual browser (Vite on :1420), measuring overlaps from `getBoundingClientRect` after fit-view has applied (background tabs throttle it). **Testing React Flow under jsdom:** `test-setup.ts` stubs `ResizeObserver`/`DOMMatrixReadOnly`; click graph elements with `fireEvent.click`, not `userEvent` (d3-drag throws on synthesized mouse-downs); pan/zoom gestures are the library's job and are not tested.
- Test captures are built in code (`backend/tests/pcap_factory.py`); regenerate the sample with `tests/fixtures/build_fixtures.py`. In tests always set explicit Ether MACs (otherwise Scapy tries ARP resolution).

## Detection engine (backend/app/detection)
- `detect_threats(analysis_result, config=None)` runs detectors that are pure functions of the `AnalysisResult` (no packets, no I/O). One detector per file, all subclass `BaseDetector`; `DetectorEngine` isolates failures.
- All thresholds/weights live in `detection/config.py` (`DetectionConfig`). Confidence = weighted mean of 0..1 factor scores (`severity.ramp`) mapped to [0.30, 0.95]; severity = band of confidence, capped per detector. Never emit certainty.
- Every `Finding` needs: evidence, reasoning, caveats (benign explanations), hedged wording ("possible", "consistent with", "requires investigation"), and a non-destructive recommendation. `tests/detection_helpers.assert_well_formed` enforces this.
- If a detector needs data the analysis result lacks, add a bounded aggregate to the analyzer (see `syn_pairs`, `syn_targets`, `arp_statistics`, `dns_statistics.clients`) rather than reading packets in a detector.
- Use real public IPs in tests: `ipaddress` treats 192.0.2/198.51.100/203.0.113 as private.

## AI investigator (backend/app/ai)
- Only `provider.py` (`AIProvider`) is used by the app; `gemini_client.py` is the sole Gemini-specific module. Config: `AiSettings` in `app/config.py` (`GEMINI_API_KEY`, `GEMINI_MODEL`, from env/`.env`).
- `Investigator.investigate_analysis(analysis, findings)` builds a bounded bundle via read-only `tools.py` (fixed allowlist, sanitised), calls the provider, validates with pydantic, then grounds the output: IPs not in the evidence -> rejected; uncited numbers dropped from `evidence`; overclaims rejected; command/blocking steps removed; severity capped at the highest local finding.
- Tests mock the provider/SDK (`tests/ai`); no key or network needed. Manual run: `.venv/bin/python -m app.ai capture.pcap`.

## Live capture (backend/app/capture, docs/live-capture.md)
- `LiveCaptureManager` (live_capture.py) is the only owner of a capture; `sniffer.py` (`PacketSource`/`ScapySource`) is the only OS-facing code and is listen-only. Never add send/inject/block calls. Packets are also recorded to a standard PCAP/PCAPNG by `recorder.py` (see Capture library below); recording is off when no `capture_store` is passed (tests), and a recorder failure never raises into the packet path.
- Start requires an explicit `confirm=true`; AI investigation of live events is opt-in per capture and only gets aggregated evidence for one finding (thresholds + cooldown + hourly budget in `LiveConfig`).
- Rolling window: `PacketRecord`s in a bounded deque -> `analyze_records()` + `detect_threats()` every `refresh_seconds`. Tests use `FakeSource` (tests/capture/live_helpers.py); live packets must be dissected from bytes (`FakeSource.emit` does this).

## Reports (backend/app/services/report_*.py, app/api/reports.py, app/migrations.py)
- A report is a self-contained JSON snapshot (`ReportContent`) stored in SQLite table `reports`; schema comes from `app/migrations.py` (append a new `(version, fn)`; never edit a released one; `PRAGMA user_version`). Access is parameterised SQL via `ReportStore`.
- Reports hold conclusions, evidence, concise detector reasoning steps and recommendations only - never model internals. AI summary is opt-in (`run_ai`) and its failure never prevents saving.
- Exports (html/md/json) escape all dynamic text; export files are written only to `settings.reports_dir` with generated names. Deleting requires `confirm=true` (UI shows a confirmation dialog first).

## Investigate Network (backend/app/services/network_*.py, app/ai/network_health.py, desktop/src/pages/Investigation.tsx)
- One click -> `POST /api/analyses/{id}/investigate-network` (`use_ai` optional). Three layers: local metrics + rule-based rating (`network_evidence.py`, always produced, no AI), the grounded Gemini answer (`NetworkInvestigator`), and an honest fallback (`status`: completed / local_only / ai_failed). A failed or rejected AI answer never hides the local layer.
- Grounding: the model may cite only ids PacketMind issues (`rtt.avg`, `finding:`, `anomaly:`, `domain:`...); every displayed number comes from the local metric table, never model text. Rating stays within one step of the local rating; confidence is capped by evidence strength; there is no reasoning field in the schema or UI. Unsafe steps (commands, firewall/routing/config changes, blocking, deleting) are removed before other checks; overclaims or unknown IPs/numbers reject the answer.
- Rating: Degraded = clearly worse than this computer's usual; Poor = that AND bad in absolute terms (or no history); Unknown = nothing measurable (never Healthy by default). "Normal" = sample-weighted pooled means over up to 30 earlier captures, needs >=5 (`PerformanceHistory.network_normals`).
- Only a summary of measurements goes to Gemini (never the capture or its file name); the UI shows `disclosure`. State lives in `InvestigationContext` (dropped when the loaded capture changes). Tests: `tests/ai/test_network_*`, `tests/test_api_network_investigation.py`, `pages/investigation.test.tsx`.

## Network Intelligence Dashboard (backend/app/analysis/dashboard.py, app/models/dashboard.py, desktop/src/pages/Dashboard.tsx, components/dashboard/)
- `GET /api/analyses/{id}/dashboard?range=5m|15m|1h|all` and `GET /api/live/dashboard`: `build_dashboard(result, findings, anomalies, range)` is a pure aggregation of existing results (no packets, nothing re-measured); every list is capped (top 10 domains, 20 active connections, 15 activity items, <=300 timeline bins), so size does not grow with the capture. React only renders it (`useDashboard`).
- Ranges are measured back from the capture's last packet. Shorter ranges rebuild per-domain latency from `flow_samples` that started in the range, DNS latency from `lookup_samples`, traffic from timeline bins; "Capture duration" uses the capture-wide figures. A range longer than the capture = whole capture (+ note). History anomalies are not range-filtered.
- Health score is a quick, explainable 0-100 heuristic (deductions listed, same thresholds as `HealthThresholds`/investigation guides); `Unknown` with no score when nothing is measurable - never Healthy by default. The full analysis is Investigate Network.
- Suspicious connection = an endpoint named by a visible finding ("possible, requires investigation"). Active = TCP not CLOSED/RESET, UDP seen in the last 30 s of the window. Live has no history anomalies. Tests: `backend/tests/test_dashboard.py`, `desktop/src/pages/dashboard.test.tsx`; `mockApi` defaults `getDashboard`/`getLiveDashboard`.


## Capture library & live recording (backend/app/capture/recorder.py, services/capture_store.py, services/capture_library.py, api/captures.py, desktop/src/pages/Captures.tsx)
- One `captures` table (migration v3) + files in `settings.captures_dir`. File names on disk are **generated** (`packetmind_<capture|import>_<date>_<time>_<id>.pcap[ng]`, created O_EXCL, mode 0600); user-supplied names are only sanitised display text (`original_filename`). `CaptureStore.path_of` re-checks the path stays inside the folder. The API never returns filesystem paths. Statuses: CAPTURING, COMPLETED, ANALYZING, ANALYZED, FAILED.
- Live: `LiveCaptureManager(capture_store=, on_capture_saved=)`. Start creates the row + file (removed again if the interface cannot be opened); `_finish_recording` (stop/shutdown/failure, idempotent) closes the writer, verifies the file (`verify_capture_file`), finalises the row and triggers the standard analysis of the saved file. Write failures (disk full) stop the capture (`capture_write_failed`) and mark FAILED - never reported as saved. The live path skips the rolling-window history record when a file was saved (the file's analysis records it, so baselines are not double counted).
- Import: `POST /api/analyses` (unchanged route) validates extension (.pcap/.pcapng/.cap) + signature, streams to `uploads_dir`, then **moves** the file into the library (`X-Save-To-Library: false` keeps the old analyse-once-and-delete behaviour). `AnalysisJobManager.submit(..., keep=True, capture_id=)` never deletes a library file; `capture_library.record_analysis(job)` writes status/summary back. Analysis, re-analysis (`POST /api/captures/{id}/analyze?force=true`) and live recordings all use the same `analyze_pcap` + detectors; the stored bytes are never modified. Job failures show a generic "may be corrupted or unsupported" message (no internal names).
- Export: `POST /api/captures/{id}/export` validates the destination chosen in the native dialog (absolute, no `..`, existing folder, not the managed folder, not a symlink, overwrite only with `overwrite: true`, extension forced to match the format), copies via temp file + rename. Delete needs `confirm=true`. The UI uses `@tauri-apps/plugin-dialog` (`lib/exportCapture.ts`; browser fallback = download URL); capability `dialog:allow-save/open`.
- Tests: `tests/capture/test_recording.py`, `tests/test_api_captures.py` (autouse `capture_library` fixture gives every test its own folder/DB; tests never touch the real `captures/`), `desktop/src/pages/captures.test.tsx` (mock `@tauri-apps/plugin-dialog`; set `window.__TAURI_INTERNALS__` to take the native path). `LiveCapture` takes its API from `ApiContext` unless an `api` prop is passed.


## Settings (backend/app/models/app_settings.py, services/{app_settings,effective_config,secret_store,ai_usage,storage,database_admin,diagnostics}.py, api/settings.py, desktop/src/{state/SettingsContext.tsx,components/settings,pages/Settings.tsx})
- **One typed model** `AppSettings` (pydantic, `extra="forbid"`, bounds on the fields) stored as one JSON row (migration v4 `app_settings`; also `ai_usage` counters). Backend code reads it via `current_settings()` or the builders in `effective_config.py` (`detection_config`, `analysis_options`, `skipped_analyzers`, `health_thresholds`, `baseline_config`, `apply_performance_settings`, `log_level`). **A field exists only if the backend consumes it**; anything unsupported is listed in `UNAVAILABLE` (shown disabled with a reason, never stored). With default settings every builder returns exactly the previous code defaults. Never add a setting without wiring it and a test that proves the behaviour changes.
- Consumers: `DetectorEngine()` (default config + per-detector `min_confidence_by_detector`), `analyze_pcap/analyze_records` (options, skipped analyzers, max packets, performance switches), `assess_health`/dashboard/network evidence (slow thresholds), `PerformanceHistory` (`config_provider`/`gate` on the app-wide instance), `LiveCaptureManager` (defaults, size/duration limits, rotation, headers-only via `privacy.store_payloads`, storage limit via `before_recording`, AI auto severity + daily budget), `GeminiClient` (model/timeout/key overlay; `AiUsage` gate = AI master switch, daily limit, cache, counters; an injected fake SDK client opts out), reports (anonymize IPs), web activity/dashboard (`domain_visibility`), logging (`reconfigure_logging`), startup (retention prune, optional auto cleanup) and shutdown (clear temp uploads).
- **Secrets**: the Gemini key is write-only into the OS keychain (`secret_store.py`; `AiSettings.api_key_value()` prefers it over `GEMINI_API_KEY`). No API returns it; diagnostics redact it. Every file the user names (export, backup, diagnostics) goes through `services/paths.validate_destination`; restore validates the SQLite file and saves a safety copy; clear/cleanup/delete/restore/reset need `confirm=true`; PCAPs are only deleted by the explicit "delete capture files" option or a confirmed cleanup.
- **UI**: `SettingsProvider` holds saved + draft; `validateSettings` uses the limits the backend sends (`constraints`), so rules live in the model. `lib/defaultSettings.json` and `test/settingsPayload.json` are generated from the model (a backend test fails if they drift). Shared settings (RTT, handshake, performance, domain tracking, payloads, cache) are bound to one key and labelled "the same setting as ...". The theme, time format and request timeout apply as soon as they are saved.
- Tests: `backend/tests/test_settings.py` (autouse `app_settings` fixture = isolated DB + in-memory keychain), `desktop/src/pages/settings.test.tsx`.

## Packaging (docs/packaging.md, scripts/build-*.sh, desktop/src-tauri/src/{lib,backend}.rs, backend/packaging/)
- The installed app bundles a PyInstaller one-folder backend (`Contents/Resources/backend/packetmind-backend`; Tauri flattens the mapped folder) and starts it itself: free loopback port + random per-launch token (`X-PacketMind-Token`, enforced by `require_token` in `app/main.py` when `PACKETMIND_API_TOKEN` is set; `/api/health` and CORS preflight stay open), readiness = real `/api/health` answer, restart <=3x, SIGTERM on quit, parent-death watchdog (`PACKETMIND_PARENT_PID`). Rust unit tests: `cargo test` in `src-tauri`.
- Everything writable goes to `PACKETMIND_DATA_DIR` (Application Support when installed). A frozen backend refuses to start without it and reads no `.env`. In development (no env) paths are the project folders as before; debug Tauri builds bundle no backend and use `python main.py` on :8765 with no token.
- Frontend: `lib/bootstrap.ts` + `components/layout/Startup.tsx` fetch address/token from the shell before the app renders; every backend call goes through `apiFetch` in `api/client.ts` (never call `fetch` on the backend directly). Browser-download fallbacks cannot send the token; they are only used outside the desktop shell.
- `pyshark`/TShark are NOT used (diagnostics only reports whether tshark exists). Runtime deps: `backend/requirements.txt`; build/test deps: `requirements-dev.txt`. New hidden imports/data for PyInstaller go in `backend/packaging/packetmind-backend.spec`; re-run `scripts/verify-backend-bundle.sh` after dependency changes.
